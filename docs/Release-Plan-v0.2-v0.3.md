# S3 Explorer v0.2–v0.3 版本拆分与交付计划

本文记录 S3 Explorer `0.2.1` 至 `0.3.4` 的版本边界、需求拆分、验收标准、提交策略和完成情况。每完成一个版本点，都应同步更新本文中的状态、提交和验证结果。

## 状态说明

| 状态 | 含义 |
| --- | --- |
| 已完成 | 需求已提交，并完成该版本要求的全量测试与 Release 构建 |
| 进行中 | 需求边界已经确认，正在实现或等待提交 |
| 未开始 | 只有计划，尚未写入代码 |
| 受阻 | 功能代码已完成，但仍有明确的环境或外部依赖门禁 |

## 提交与回滚规则

1. 每个版本号对应一个独立、可回滚的需求边界。
2. 默认每个版本 1 个最终提交；只有核心实现与独立兼容修复确实需要单独审阅或回滚时，允许 2 个提交。
3. 版本号、代码、测试、配置和本版本直接相关的文档放在同一版本边界内。
4. 不把下一个版本的功能提前混入当前版本。
5. 每个版本完成后必须运行完整测试和独立 Release 构建；局部测试不能替代全量验证。
6. UI、导航或共享控件变更还需要桌面运行时验证；截图因锁屏无法执行时，应明确标记为环境受阻。

## `0.2.2` 删除、复制与受限权限兼容策略

**状态：已完成**

### 已交付需求

- `ListBuckets` 返回 403/AccessDenied 时，识别为“服务可达但账号无权列出全部 Bucket”。
- 允许 write-only 或受限 IAM 用户继续使用已知 Bucket 路径。
- Multi-Object Delete 不受支持、被拒绝或返回兼容性错误时，自动降级为逐对象删除。
- 用户关闭 Multi-Object Delete 时直接使用逐对象删除。
- 超过单次服务端 Copy 限制的大对象自动使用 Multipart Copy。
- Multipart Copy 计算符合 S3 分片数量和大小约束的 part size。
- Multipart Copy 失败时尽力执行 `AbortMultipartUpload`，并保留原始错误。
- 增加受限权限、删除降级和 Multipart Copy 策略单元测试。

## `0.2.3` 大列表、特殊 Key、长路径与导航稳定性

**状态：受阻；功能已提交，全量测试和 Release 构建通过，仅视觉截图内容检查待补。**

### 需求范围

- 对象分页大小可配置，范围控制在兼容服务可接受的边界内。
- 对象列表设置内存保护上限，默认避免一次性保留百万对象。
- 使用基于 Key 和目录标识的 O(1) 去重，避免大列表下的重复线性扫描。
- 达到内存上限后停止自动加载，并在 UI 中明确提示。
- 快速连续切换连接、Bucket 和目录时，旧请求必须取消且不能覆盖新导航结果。
- 刷新与导航并发时只能保留当前导航上下文的结果。
- 列表、上传和下载取消必须保持幂等，不得访问已释放的 `CancellationTokenSource`。
- 正确保留中文、空格、`+`、`%` 等合法 S3 Key 字符。
- 将 Windows 非法文件名字符、保留设备名和尾部空格/点安全映射到本地路径。
- 支持 Windows 扩展长度路径，避免 260 字符限制。
- 阻止 `..` 等对象 Key 片段逃出用户选择的下载根目录。
- 文件夹递归枚举同样受对象数量和内存上限保护。

## `0.3.1` 可恢复传输任务与队列生命周期

**状态：未开始。**

### 需求范围

- 建立可序列化的传输任务模型，区分上传、下载、文件夹批次和任务状态。
- 持久化等待中、暂停、运行中断和失败任务，不持久化明文凭据。
- 应用启动后恢复未完成任务；原运行中任务恢复为可继续或可重试状态。
- 支持暂停、继续、取消和单任务重试。
- 支持失败任务一键重试。
- 任务状态转换必须线程安全、幂等并可测试。
- 关闭程序时提供等待完成、暂停并退出、取消任务、返回程序四种选择。
- 单个任务失败不能导致队列工作线程停止。

### 计划提交

1. `feat: add persistent recoverable transfer engine`
2. `feat(ui): add transfer lifecycle controls`（UI 与关闭策略需要独立回滚时）

### 验收标准

- 强制结束应用后重新启动，未完成任务仍可见且状态正确。
- 暂停任务不再读写网络；继续后从安全检查点恢复。
- 取消和重复取消不会抛出未处理异常。
- 任务存储文件不包含 Secret Key、Session Token 或 Authorization 数据。
- 完整测试和独立 Release 构建通过。

## `0.3.2` 下载续传、原子落盘、限速和电源管理

**状态：未开始。**

### 需求范围

- 下载使用临时文件，完成校验后原子重命名到目标路径。
- 支持基于本地临时文件长度和远端对象条件的 Range 断点续传。
- 远端 ETag、长度或版本变化时拒绝错误续传并重新开始。
- 取消或失败时保留可恢复临时文件；用户明确删除任务时可清理。
- 上传和下载分别支持全局限速，`0` 表示不限速。
- 并发数、分片大小、重试次数和指数退避可配置。
- 活跃传输期间阻止系统自动睡眠，队列空闲后恢复系统默认行为。
- 程序异常退出后不留下“已完成但未重命名”的伪成功文件。

### 计划提交

1. `feat: add resumable atomic downloads`
2. `feat: add transfer throttling and power management`

### 验收标准

- 中断下载后可以从已验证的偏移继续。
- 下载完成前目标正式文件不可见或不被覆盖。
- 同名目标替换符合原子性约束，失败时原文件保持不变。
- 限速误差在可接受范围内，取消时不会长时间等待限速器。
- 活跃传输时电源请求生效，任务结束后可靠释放。
- 完整测试和独立 Release 构建通过。

## `0.3.3` Multipart 状态、可靠 Abort 与残留清理

**状态：未开始。**

### 需求范围

- 持久化 Multipart Upload 的 Bucket、Key、UploadId、分片大小、已完成分片及 ETag。
- 应用重启后核对远端已上传分片，并只补传缺失分片。
- 上传取消时可靠执行 `AbortMultipartUpload`。
- 网络错误导致 Abort 失败时记录待清理状态，不把任务标记为已清理。
- 扫描当前连接下未完成 Multipart Upload。
- 支持按 Bucket、Key、创建时间筛选和清理残留上传。
- 清理操作必须显式确认，并显示将释放的上传数量和已知大小。
- Multipart Copy 使用相同的清理与状态基础设施。

### 计划提交

1. `feat: persist and resume multipart uploads`
2. `feat: add incomplete multipart upload cleanup`

### 验收标准

- 重启后不会重复上传已确认完成的分片。
- 用户取消后远端 UploadId 被 Abort，或被明确记录为待清理。
- 清理扫描不会误删已完成对象。
- MinIO 集成测试覆盖创建、恢复、Abort、扫描和清理。
- 完整测试和独立 Release 构建通过。

## `0.3.4` 文件夹批次进度、失败明细和批量重试

**状态：未开始。**

### 需求范围

- 文件夹上传和下载使用父批次任务聚合子任务。
- 显示文件总数、已完成数、失败数、跳过数、总字节和已传输字节。
- 单文件失败不终止整个批次。
- 记录每个失败文件的相对路径、错误类别、HTTP 状态、服务错误码和可重试性。
- 支持只重试失败项、重试选中项和导出失败明细。
- 重试后批次统计必须重新计算，不能重复计数。
- 用户取消批次时取消尚未开始的子任务，并请求取消运行中的子任务。
- 大文件夹不能一次性把全部 UI 行和对象模型常驻内存。

### 计划提交

1. `feat: add resilient folder transfer batches`
2. `feat(ui): add failure details and retry actions`

### 验收标准

- 一个文件失败后，其余文件继续传输。
- “重试失败项”只重新创建失败或可重试的子任务。
- 批次总进度与子任务完成状态一致。
- 失败报告不泄露凭据或完整预签名 URL。
- 大批次 UI 保持响应，取消和关闭没有死锁。
- 完整测试和独立 Release 构建通过。

## 每个版本的通用验证门禁

1. 当前版本的新增和回归单元测试全部通过。
2. 运行完整 `dotnet test S3Explorer.sln -c Release`。
3. 运行独立 `dotnet build S3Explorer.sln -c Release`，要求 0 错误；新增警告必须解释并处理。
4. 涉及发布结构时运行根目录 `build.bat`、`publish.bat` 和 `scripts/Test-Publish.ps1`。
5. 涉及 MinIO 行为时使用隔离临时账号运行真实集成测试，并清理所有测试资源。
6. 涉及 UI、导航、传输队列或关闭流程时，在交互式桌面执行运行时验证和截图。
7. 检查 Git 状态，确保没有未提交修改、临时文件或生成产物进入提交。
8. 审计该版本只有计划内的 1–2 个提交，并确认没有跨版本功能混入。

## 计划更新规则

- 开始版本时：把状态从“未开始”更新为“进行中”，补充最终需求边界。
- 提交版本时：记录完整提交哈希和提交主题。

- 发生范围调整时：说明需求移动到哪个后续版本，不静默删除。
- 合并到 `main` 或推送后：记录目标分支、远端状态和最终 HEAD。
